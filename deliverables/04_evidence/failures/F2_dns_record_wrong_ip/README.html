F2 · The DNS record points to the wrong IP address

Run: 2026-09-30 14:07:56-14:08:14 IST on mac_vachan (DNS server + client). Break: app.subspace-67.test was pointed at 10.7.1.136 (mac_abhay: a live host, but nothing listens on 443 there): bin/gen_dnsmasq.py --app-ip 10.7.1.136, then a dnsmasq restart and a cache flush.

After restoring the record: dig -> 10.7.19.193, HTTPS 200, healthy.

Layer and why

DNS is a directory, not a connection. The DNS server answered exactly what it was configured to say, with authority and a 60 s TTL. It has no idea whether that IP runs our service. The client then did what DNS told it: opened TCP to 10.7.1.136:443. That host's kernel refused the connection (RST) because no process listens on

  1. The failure shows up at the transport layer, but its cause is a wrong DNS record. Diagnosis rule:

compare the IP dig returns with the IP you expect before debugging TCP or TLS. The 60 s TTL also means any client that looked up the name during the fault keeps the wrong answer for up to a minute (or until its cache is flushed).
