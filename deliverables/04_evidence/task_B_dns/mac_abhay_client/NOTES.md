# Task B: this Mac resolves names through OUR DNS server (mac_vachan)

**What was changed** (root batch `sudo/01_dns_and_ca.sh`, one password):
`networksetup -setdnsservers Wi-Fi 10.7.23.136` (mac_vachan's IP, read from its info.json), then
`dscacheutil -flushcache; killall -HUP mDNSResponder`. Before: no manual DNS servers (DHCP gave 8.8.8.8 and 10.5.7.1,
see task_A/08 and PROJECT_DIR/original_network_settings.txt). `restore_network.sh` puts it back.

**What it shows**
| File | Proof |
|---|---|
| 01_dns_servers.txt | Wi-Fi DNS servers = `10.7.23.136` **only** |
| 02_scutil_dns_excerpt.txt | the live resolver config (`scutil --dns`, resolver #1) has a single nameserver 10.7.23.136, "Directly Reachable Address" (same subnet) |

| 05_dig_api.txt | api.subspace-67.test -> the same edge IP 10.7.19.193 |

| 00_check.txt | automatic check: SERVER = mac_vachan, answer = mac_aanya |

**Which layer**: application layer (DNS) carried over the transport layer (UDP port 53, normally; TCP 53 in file 07).

**Why**: a client must never need an IP. It asks our DNS server for the name, and the answer points at the **edge**
(mac_aanya), never at a backend. DNS is only the "phone book" step: after this answer, the client talks to
10.7.19.193 directly and never contacts the DNS server again for that connection (see the Task G capture, which
shows the DNS query/response first, then the TCP SYN to the answered IP).
