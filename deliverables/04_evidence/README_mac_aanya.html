The TLS-termination capture, explained

How: during one sudo run, tcpdump -i pktap,lo0,en0 captured both interfaces into one pcapng with Apple's per-packet metadata (interface + process name). Filter: only this Mac's HTTPS-to-itself, edge↔backend HTTP, and DNS to mac_vachan (no unrelated traffic). Traffic (see capture_traffic_commands.txt): dig, one request forced to TLS 1.2 + HTTP/1.1, then requests with curl's default TLS 1.3 (HTTP/2 and HTTP/1.1).

The client is on the edge itself, so leg 1 (curl → nginx, to our own IP) travels over the loopback interface lo0, while leg 2 (nginx → backend) leaves on en0 (Wi-Fi). Same request, two TCP connections:

Checks in the exports: the string X-Backend appears 0 times in the TCP payloads on port 443 (it's only inside encrypted records), and appears in clear on ports 3001/3002. Encrypted on the client side, plaintext on the backend side, for the same request = nginx terminates TLS.

Reading notes:

  • On lo0 each packet is captured twice (leaving the sender's socket and arriving at the receiver's socket; pktap shows curl for one copy and nginx for the other), so Wireshark labels the second copy "TCP Retransmission" / "Dup ACK". These are capture artefacts, not real retransmissions.
  • Leg 2 is plain HTTP on the Wi-Fi LAN on purpose (the lab's "private network"); in production you'd keep that network private or re-encrypt to the backends.
  • The edge→backend hop shows the edge's IP (10.7.19.193) as the source: the backends never see the client's TCP connection, only X-Forwarded-For.

Open the pcapng in Wireshark; useful display filters: tls.handshake, tcp.port==443 && tls.app_data, http && (tcp.port==3001 || tcp.port==3002), dns. Add the columns Interface name and Darwin → Process Information → Name to see lo0/en0 and curl/nginx per packet.

Notes

  • /usr/bin/curl on macOS 26 (LibreSSL 3.3.6 build) does use the System keychain: our CA is not in /etc/ssl/cert.pem, yet plain curl https://app.subspace-67.test verifies (ssl_verify_result=0); with an empty --cacert file the same request fails. So no -k and no --cacert were needed. openssl s_client does not read the keychain, so it gets -CAfile tls/ca.crt (still full validation).
  • Apple's curl has no --tlsv1.3 switch (exit 4, nothing sent); TLS 1.3 is its default anyway.
  • nginx runs as the normal user (no sudo): macOS allows binding ports < 1024 on the wildcard address. The macOS application firewall asked once to allow incoming connections for nginx (ad-hoc signed Homebrew build).
  • zone team_backends 1m; makes all 10 nginx workers share one round-robin pointer and one set of failure counters (before it, one client saw A B A A B A A B B A).
